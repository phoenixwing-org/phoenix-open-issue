# 管理员绑定与待审查计划

更新时间：2026-07-20  
状态：**已完成（归档）** — 服务端 / 前端 / 表结构点检已落地；真实飞书端到端验收仍待开放平台环境。  
范围：在飞书 OAuth 首期之上，改为「仅管理员完成绑定」；未绑定身份进入待审查队列。

> 归档说明：本文保留为二期设计与验收依据。目录总览见 [README.md](./README.md)。首期「用户自助绑定」流程已废止，参见下文与 [飞书OAuth设计.md](./飞书OAuth设计.md) 的 superseded 标注。

## 1. 背景与目标

### 1.1 现状

- 本地用户是权限、组织、审批与数据归属的唯一主体。
- 飞书登录要求 `externalIdentities` 中已有 `provider + providerSubject` 绑定。
- 用户需先本地登录，再到「设置 → 登录方式」自助绑定飞书。
- 管理员仅能查看 / 解除绑定，不能代绑或处理「未绑定却已完成飞书授权」的身份。
- 存量已批准本地账号大量未绑飞书；若未绑定时自动建号，易产生重复账号。

### 1.2 目标

1. **取消用户自助绑定**；绑定只能由管理员完成。
2. **任意未绑定用户**（新人、已批准未绑飞书的老用户）都走同一条路：飞书登录 → 待审查。
3. 待审查记录优先带入飞书侧姓名等信息；不足时由用户补填拟用用户名、姓名。
4. 管理员可修改用户名、姓名等，再选择：
   - **绑定已有本地账号**，或
   - **新建本地账号**（前端点检不存在 + 后端再查 + DB `UNIQUE`）。
5. 保持可扩展：后续钉钉 / 企业微信等 OAuth 复用同一套表与队列，不按提供方各建一套业务表。

### 1.3 非目标（本期不做）

- 按邮箱 / 手机号 / 姓名自动认领已有账号。
- 飞书通讯录同步、组织架构自动映射。
- 保存飞书 access / refresh token。
- 无密码纯第三方账号（首期新建账号仍应具备本地密码策略，具体规则见实施时确认）。

## 2. 目标流程

```
用户点「飞书登录」
  → OAuth 成功，得到稳定身份（provider + providerSubject）
  → 已绑定且本地账号可用 → 签发登录票据（现有逻辑）
  → 未绑定
       → 写入 / 更新「待审查」记录（不建号、不登录）
       → 预填飞书姓名、邮箱等；必要时引导用户补填用户名、姓名
       → 提示「已提交，等待管理员处理」

管理员在待审查列表
  → 可改拟用用户名、姓名等
  → 绑定已有用户 或 新建用户（双重查重）
  → 写入 externalIdentities（linkSource=admin）
  → 待审查记录标记为已处理

用户再次飞书登录 → 成功
```

### 2.1 人群覆盖

| 人群 | 行为 |
| --- | --- |
| 新人（无本地账号） | 飞书登录 → 待审查 → 管理员新建并绑定 |
| 老用户（已批准未绑飞书） | 同样飞书登录 → 待审查 → 管理员绑到已有账号（或必要时新建） |
| 已绑定用户 | 直接登录（仍校验 `approved` / `disabled`） |

### 2.2 与「用户批准」的关系

- 待审查队列是 **第三方身份 ↔ 本地用户** 的绑定审批，不是替代 `users.approved`。
- 若管理员选择「新建本地账号」：可在同一事务内 `approved=1` 并完成绑定（推荐默认直接可用）；若产品要求仍走组织人员「批准」，可配置为新建后 `approved=0`，绑定暂存至批准通过——**实施前二选一，默认建议新建即批准+绑定**。
- 已批准老用户不会再次进入 `users.approved=0`；只进待绑定队列。

## 3. 多提供方：是否同一张表？

**结论：是。绑定结果与待审查都应做成「按 `provider` 区分的通用表」，不要为每个 OAuth 系统各建一套业务表。**

| 数据 | 表 | 说明 |
| --- | --- | --- |
| 已绑定身份 | 现有 `externalIdentities` | 已有 `provider` + `UNIQUE(provider, providerSubject)`，钉钉等直接加 provider 枚举与 Provider 实现即可 |
| OAuth 短事务 / 登录票据 | 现有 `oauthLoginAttempts` / `oauthLoginTickets` | 已有 `provider` 字段 |
| 未绑定待审查 | **新建** `externalBindRequests`（名称可调） | 同样带 `provider`；生命周期与「已绑定」不同，不宜硬塞进 `externalIdentities`（该表 `userId NOT NULL`） |

理由：

1. 身份匹配规则统一：`provider + providerSubject`，禁止用展示名/邮箱自动合并。
2. Provider 差异只留在 `packages/server/src/auth/providers/*`（换票、用户信息字段映射）。
3. 管理端待审查列表可按提供方筛选，UI/API 一套复用。
4. 飞书特有字段（`openId` / `unionId` / `tenantKey`）继续作为通用列或 `metadataJson` 快照；其他提供方把稳定 ID 写入 `providerSubject`，扩展字段进 metadata。

**不要**把待审查行直接插进 `externalIdentities` 再留空 `userId`（需改约束、状态机更乱）。绑定成功后再插入 / 激活 `externalIdentities`，待审查表只负责排队。

## 4. 数据模型草案

### 4.1 `externalBindRequests`（待审查）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `provider` | 如 `feishu`，后续可扩展 |
| `providerSubject` | 与绑定表相同的稳定主体 |
| `tenantKey` / `openId` / `unionId` / … | 快照，便于管理员核对 |
| `displayName` / `email` / `avatarUrl` | 提供方快照 |
| `proposedUsername` | 用户或管理员填写的拟用用户名 |
| `proposedDisplayName` | 拟用姓名（可预填飞书姓名） |
| `status` | `pending` / `bound` / `rejected` / `expired` |
| `boundUserId` | 处理后关联的本地用户（可空） |
| `handledByUserId` / `handledAt` / `note` | 审计 |
| `createdAt` / `updatedAt` / `lastSeenAt` | 重复飞书登录时更新 `lastSeenAt`，不重复堆多条 pending |

约束建议：

- `UNIQUE(provider, providerSubject)` 在 `status='pending'` 上用部分唯一索引；若方言不支持，则应用层保证「同一主体仅一条 pending」，重复登录只更新快照与补填字段。
- 不保存任何 OAuth 令牌。

### 4.2 `externalIdentities` 调整

- `linkSource`：继续使用 `admin`（本期绑定一律管理员）；废弃用户路径的 `self` 写入（历史数据可保留）。
- 管理员解绑逻辑保持；解绑后同一飞书身份再次登录重新进入待审查。

### 4.3 备份

- `externalBindRequests` 中 `pending` 是否进完整备份：建议进入（避免迁移丢单）；临时 OAuth 事务表仍不进备份。

## 5. 接口与权限（草案）

### 5.1 公开 / 登录流

| 变更 | 说明 |
| --- | --- |
| 登录回调未绑定 | 不再仅返回 `identity_not_bound` 死胡同；创建或更新 `externalBindRequests`，前端引导补填（若需要）并展示「等待管理员」 |
| 可选补填接口 | `POST /api/auth/oauth/:provider/bind-request/profile`（凭短期 ticket 或 request token，仅能改自己的 pending 记录的拟用字段） |

### 5.2 移除 / 收紧

| 接口 | 处理 |
| --- | --- |
| `POST /api/auth/oauth/:provider/link/start` | 对普通用户关闭；或整段移除自助绑定 |
| 用户设置「绑定飞书」按钮 | 移除；可保留「查看已绑定 / 申请解绑」或仅只读 + 联系管理员 |

### 5.3 管理员

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/external-bind-requests` | 待审查列表（可按 provider、status 筛选） |
| `PATCH` | `/api/admin/external-bind-requests/:id` | 修改拟用用户名、姓名、备注 |
| `POST` | `/api/admin/external-bind-requests/:id/bind` | body: `{ userId }` 绑到已有用户 |
| `POST` | `/api/admin/external-bind-requests/:id/create-and-bind` | body: 新建用户字段；服务端双重查重后建号并绑定 |
| `POST` | `/api/admin/external-bind-requests/:id/reject` | 拒绝 |
| `GET` | `/api/users/username-available?username=` | 前端点检（管理员鉴权）；创建接口内必须再查一次 |

所有管理员接口要求系统管理员（与现有 `assertSystemAdminAsync` 一致）。

### 5.4 新建账号查重

1. 前端：失焦或提交前调用 `username-available`。
2. 后端 `create-and-bind`：`SELECT` 用户名是否存在 → 不存在再 `INSERT`。
3. DB：`users.username UNIQUE`；冲突映射为 409，提示刷新后重试。

## 6. 前端改动要点

1. **登录 / OAuth 回调**：未绑定 → 待审查说明页；必要时简易表单补用户名、姓名。
2. **设置 → 登录方式**：去掉自助绑定；展示已绑定摘要；解绑策略与现网一致或改为「仅管理员可解绑」（实施时确认）。
3. **组织 / 人员管理**：增加「第三方登录待审查」入口（列表 + 详情：绑已有 / 新建）。
4. 文案与巡游帮助同步更新（`pageHelp` 等）。

## 8. 安全与一致性（继承首期原则）

- 匹配只用 `provider + providerSubject`，不用邮箱/姓名自动绑定。
- 租户白名单（飞书 `tenant_key`）在进入待审查前仍须校验。
- 回调不向前端暴露授权码或第三方令牌；补填若需凭证，只用短期 request token。
- 绑定与新建在同一 DB 事务中完成，避免「建了用户却没绑上」。
- 审计：记录处理人、时间、绑到的 `userId`、`linkSource=admin`。

## 10. 产品拍板（已落地）

1. 管理员「新建并绑定」时本地用户默认 `approved=1`。
2. 新建账号初始密码：管理员在处理对话框中指定（至少 6 位）。
3. 用户侧仍可自助解除绑定；解绑后再飞书登录重新进入待审查。
4. 待审查过期清理：本期未做自动过期，可后续按 `lastSeenAt` 加策略。
5. **不在本期**：禁用本地密码登录、仅允许飞书（尚无开关）。
