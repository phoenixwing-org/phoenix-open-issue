# 多人权限与列表筛选加固

> 状态：已实施（2026-07-15）  
> 适用版本：未发布版本（v0.4.0 之后）

## 1. 背景与目标

本次加固解决三类问题：

1. 组织架构中的系统权限「查看」原先只保存为 `users.systemRole=viewer`，业务接口仍主要按列表成员角色判断，可能出现系统角色是查看、但因列表角色为 editor/owner 仍可写入的情况。
2. 列表、Issue、点检和推送的部分按 ID 查询/写入接口缺少统一权限校验，存在非成员读取或操作不属于自己的数据的风险。
3. 问题列表与列表管理需要在数据已全部拉到前端的前提下提供统一筛选，并在结果超过 30 条时分页，避免长页面持续滚动。

## 2. 权限模型

权限由系统角色和列表角色共同决定，系统角色先于列表角色生效：

1. `systemRole=admin`：系统管理员，可跨列表读写并管理系统配置。
2. `systemRole=viewer`：全局只读上限。即使列表角色是 owner、admin 或 editor，也不能执行任何写操作。
3. `systemRole=editor`：按所在列表的成员角色授权。

### 2.1 列表角色权限矩阵

下表适用于 `systemRole=editor`；系统管理员全部允许，系统查看用户除读取外全部拒绝。

| 动作 | owner | admin | editor | reporter | viewer |
| --- | --- | --- | --- | --- | --- |
| 查看列表、Issue、点检和推送记录 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 编辑/归档列表 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 删除列表 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 管理成员 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 创建 Issue | ✅ | ✅ | ✅ | ✅ | ❌ |
| 修改 Issue、关注度和点检 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 发起推送 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 审批目标列表的推送 | ✅ | ✅ | ❌ | ❌ | ❌ |

系统级组织、用户审批、数据字典、功能表写入、数据库导入/修正、测试数据和后台测试均只允许系统管理员操作。

推送接受后是同一 Issue 的多列表关联：Issue 主字段和点检按**源列表**角色校验；目标列表成员只能按目标列表权限调整该链接自己的关注度。列表接口逐行返回有效能力，前端不会为无源列表写权限的关联 Issue 显示编辑、点检或再次推送入口。

## 3. 已实施的接口加固

### 3.1 统一有效权限

- core 新增 `canPerformListAction`，前后端使用同一套系统角色 + 列表角色规则。
- server 新增统一访问校验：活动用户、列表成员、Issue 可读性、列表动作和系统只读写入限制。
- 前端根据有效权限隐藏新建、编辑、删除、成员管理、点检、推送和审批入口；后端仍独立强制校验，不能依赖前端隐藏。

### 3.2 越权读取与写入

- 列表详情、成员、归档列表、Issue 详情、点检列表、推送预览/记录/收件箱均校验实际访问者。
- 非系统管理员只能查看自己是成员的列表及其关联 Issue；不能通过猜测 ID 访问其他列表数据。
- Issue 排序只允许更新当前列表已关联的 Issue，拒绝夹带其他 Issue ID。
- 关注度写入按当前链接所在列表校验修改权限。
- 数据字典和功能表的新增、修改、删除、导入，以及测试数据写入改为仅系统管理员。

### 3.3 认证状态

- 用户增加 `tokenVersion`。禁用账号、撤销审批、本人修改密码或管理员重置密码时递增，已签发的旧 JWT 立即失效。
- 每个认证请求都会复查账号存在、已批准、未禁用且令牌版本一致。
- 备份导入时令牌版本统一递增，导入前签发的令牌不会沿用到恢复后的数据库。
- 启动基础种子不再自动执行 `approved=1`，新注册用户必须由管理员明确批准。
- 生产启动要求至少 32 位且非示例值的 `JWT_SECRET`，以及至少 12 位且非示例值的 `INITIAL_ADMIN_PASSWORD`。

### 3.4 事务和并发

- 创建列表与写入 owner 成员在同一事务中完成。
- 创建 Issue 与写入主列表链接在同一事务中完成；自动编号遇到唯一键并发冲突时最多重试 3 次。
- 推送审批使用条件更新 `status='pending'`，重复/并发审批仅一个请求成功。
- 接受推送与创建 `issueListLinks` 在同一事务提交，并依靠唯一索引避免重复链接。

## 4. 筛选与分页

### 4.1 问题列表

- 前端分批拉取列表的全部 Issue（每批 500），筛选和分页均在前端完成。
- 支持编号/标题/描述搜索，以及状态、优先级、严重度、分类和「只显示不关注」筛选。
- 默认每页 30 条，可切换 30/50/100；超过 30 条显示分页。
- 切换筛选、每页条数或列表时回到第 1 页；结果减少时自动修正越界页码。

### 4.2 列表管理

- 支持按名称、描述、负责人搜索，按列表类型筛选，并可一键清除。
- 默认每页 30 条，可切换 30/50/100；分页序号连续。
- 正常列表和已删除列表切换时重置页码；显示筛选结果数和总数。

## 5. 回归验证

新增 HTTP/API 回归覆盖：

- 系统查看用户拥有列表 editor 角色时，可读取但所有写入返回 403。
- 非成员读取列表、Issue、点检和列表推送历史返回 403。
- 目标列表 editor 审批推送返回 403。
- 两个并发审批请求只有一个成功，且目标链接只有一条。
- 启动基础种子不会批准待审批账号。
- 账号禁用后，禁用前签发的令牌返回 401。

发布前必须通过：

```bash
pnpm test
pnpm build
git diff --check
```

## 6. 后续仍值得完善

以下事项不影响本次权限与筛选目标，建议后续按优先级推进：

1. 为 Controller 增加统一的请求体运行时校验和错误格式，避免非法枚举或 `NaN` 页码进入 SQL。
2. 为 PostgreSQL 补充稳定 CI 环境，持续运行权限、事务和并发集成测试；当前无连接时 PG 用例会跳过。
3. 在确认历史脏数据已修复后逐步启用外键约束，并补充成员 `(listId,userId)`、推送查询等索引。
4. 将 `ListDetailView`、`IssueDetailView` 和 `SettingsView` 拆分为更小的业务组件，降低维护成本。
5. 拆分 Element Plus/XLSX 等前端大包；当前生产构建仍会报告主 chunk 超过 500 kB。
6. 清理旧文档中“推送复制”“删除级联”等过期描述，持续让 API 参考与实际行为一致。
