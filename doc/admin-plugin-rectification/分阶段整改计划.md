# 分阶段整改计划

状态：active

## 1. 整改原则

- 先冻结继续重写页面，确认基线后再实施；
- 不直接 merge `legacy`，不继续扩展 Host 中的 `oip-*` 页面；
- 先把业务代码所有权迁回插件仓库，再谈在线安装包；
- Admin 已经适配 Wing 0.6，Open Issue 只迁业务页面，不迁自己的 Workbench 壳；
- 严格执行“第一遍原样迁移页面，第二遍替换 Host 接口”；
- 每阶段都必须能独立回退；
- 两个 Phoenix Admin 工作区现有改动先保留，不做破坏性清理。

## 2. D0：决策冻结

目标：形成明确的产品和迁移边界。

产出：

- 确认页面基线提交和截图集合；
- 确认插件首版页面范围；
- 确认编译期插件作为第一交付形态；
- 把 `legacy` Wing 拆区与 Host `oip-*` 页面标为技术试验，不再新增产品功能；
- 修订正式的 `PhoenixAdmin插件改造计划.md`，删除“重新实现页面”含义并加入保真门禁。

退出条件：维护者确认本目录 README 中的三个决策。

## 3. D1：现有能力盘点与契约冻结

目标：在写迁移代码前知道哪些能力共享、哪些由 Host 替代。

产出：

- 逐页组件/Store/API/权限依赖清单；
- 独立版与 Host API 字段映射；
- Host Web SDK 与 Node SDK 的最小接口；
- 路由、菜单、能力码、数据表和 migration 的稳定 ID；
- 页面金线与交互验收清单；
- 标记 `packages/admin-plugin` 中需修正的兼容范围，例如当前 manifest 的 Wing 范围仍是 `<0.6.0`，而 Host/legacy 已在使用 0.6.0。

退出条件：插件页面不得直接 import Host 内部目录；Host 不需要理解 Open Issue 业务字段。

## 4. D2-A：前端页面原样迁移

建议切片：**列表管理 → 列表详情 → Issue 查看/编辑弹层**。

选择这条链路的原因是它能同时验证：

- 列表与 Issue 的主业务链；
- 原表格、筛选、弹层和点检的页面保真；
- 前端插件是否真的脱离了独立 AppShell，并作为普通 View 进入 Admin Main；
- 页面及其依赖闭包能否在不重写界面的情况下迁入插件包。

实施约束：

- 从金线页面及其组件依赖闭包原样提取，不从 Host `oip-*` 页面反向补功能；
- 暂时通过兼容 facade 维持页面原有请求、auth、用户、字典和路由调用签名；
- 整个业务页面先放 Main；
- 不引入新的 Primary/Secondary/Properties/Bottom；
- Host 只保留薄注册入口，通过包依赖加载插件 View。

退出条件：该链路在兼容 facade 或固定数据下通过视觉与交互对照；页面模板、样式和组件结构没有未经说明的改变。

## 5. D2-B：逐项替换 Host 接口

目标：在 D2-A 页面金线保持不变的前提下，完成 Admin 平台接入。

建议替换顺序：

1. 路由前缀、Tab 打开/关闭和返回路径；
2. 请求客户端与统一错误格式；
3. Host actor、登录状态和 capability；
4. Host 用户与部门；
5. Host 字典、通知、确认框、文件与审计关联；
6. 最终 `/admin/phoenix-open-issue/*` API 字段映射。

每替换一项，都重新执行 D2-A 的页面截图与交互清单。优先在 adapter 内兼容原页面调用签名，不要求页面迎合 Host 的内部数据结构。

退出条件：该链路的视觉、交互、权限和真实 Host 数据/API 对照全部通过。

## 6. D3：后端插件归位

目标：让 Open Issue 后端代码由本仓库插件包拥有，Host 不再保存业务副本。

产出：

- Midway 后端插件入口；
- Controller、Service、Entity、migration 和健康检查；
- Host actor、用户/部门、审计、字典、任务等 adapters；
- `oip_` 数据所有权与卸载保留清单；
- Host 中 `src/modules/open-issue` 收敛为通用加载/兼容薄层，最终可移除。

退出条件：Host 只依赖插件公共入口，删除任一 Host 业务副本不会损失领域能力。

## 7. D4：剩余业务页面保真迁移

按用户价值排序建议：

当前 UI 源码已扩展到点检完整组件、推送发起/历史、8D 报告和仪表盘。D4 的剩余工作不再是重画这些页面，而是：

1. 对接真实 Midway API 并完成交互回归；
2. 评估 Open Issue 专属业务设置哪些保留、哪些复用 Host；
3. 关闭归档/回收、业务字典与诊断接口；
4. 补齐页面图标注册和正式 Pah 动态菜单；
5. 生成统一迁移审计与正式交付尺寸。

组织、登录、Host 全局设置、备份入口和测试页面按 [页面保真验收](页面保真验收.md) 中的能力归属处理，不机械复制。

退出条件：独立版核心业务回归清单全部通过，且 Admin 插件没有第二套壳和第二份业务实现。

## 8. D5：插件生命周期产品化

页面和后端边界稳定后再完成：

- 版本兼容与 upgrade plan；
- migration preview、事务、锁、恢复点和重试记录；
- `.pah-plugin` 包、SHA-256、SBOM、LICENSE/NOTICE 与 Ed25519 签名；
- 前后端产物原子落盘与受控重启；
- 禁用、卸载、重装和默认保留数据；
- 篡改包、不兼容包、断电与并发测试。

退出条件：交付形态变化不需要再修改业务页面。

## 9. 建议的分支处理

| 分支/工作区 | 建议动作 |
|---|---|
| `admin` | 作为整改主线；先更新正式计划，再新增前后端插件包 |
| `legacy` | 保留独立 Web 和 Wing 试验；不整分支合入 `admin` |
| Admin Vue/Node 的 `codex/open-issue-plugin` | 保留为已验证的 Host 原型与接口参考；迁移时逐项替换，不直接清空 |

后续若需要复用 `legacy` 内容，只按小粒度选择“与页面无关的 Wing 0.6 兼容或贡献协议代码”，并逐项说明为什么不会改变业务页面。

- 不回退、删除或覆盖任何工作区已有改动；
