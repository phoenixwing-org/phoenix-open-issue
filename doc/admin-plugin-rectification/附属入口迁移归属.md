## 2. 原 Ribbon 入口归属

| 旧入口 | 结论 | 第一遍迁移 | 第二遍适配 |
| --- | --- | --- | --- |
| 组织架构 | 复用 Host | 不迁移第二套用户、登录、角色和组织表 | Issue 列表成员引用 COOL 用户/部门；必要时提供只读业务成员视图 |
| 功能 | 属于 Open Issue | `FunctionIndexView`、筛选、排序、新建、编辑、停用、XLSX 导入和 JSON 导出原样迁移 | 数据表改为 `oip_function`，Issue 继续以稳定 `functionId` 关联 |
| 单元测试 | 属于 Open Issue 开发/维护能力 | 保留原测试文件表、运行按钮、最近结果和 HTML 报告体验，收入“维护” Primary 的测试区 | 只允许运行插件声明的测试；系统管理员、开发环境、目录白名单、单实例锁、超时和报告隔离均由执行端强制 |
| 设置 | 拆分归属 | 不整体复制，也不能整体删除 | Issue 字典、数据迁移/修正归插件；密码、登录方式归 Host；备份通过 Host 插件生命周期接入；功能导入并入功能页 |

`功能` 是业务简表，不是系统设置。现阶段不拆为独立 Function 插件，先保持旧界面、字段和 Issue 关联完整；等 Issue 插件稳定后再评估跨产品复用。

## 3. 数据库修正没有消失

旧版 `SettingsView` 确有“数据库修正”页签，包含表结构、点检、Issue 链接、字典、用户权限、关注系数、Issue 编号和 8D 报告等修正任务。当前 Admin 插件没有显示，是因为第一轮把整个设置页误归为平台设置，尚未登记路由，并非旧版没有该能力。

Admin 插件版按以下方式恢复：

- 插件安装/升级 migration 自动执行可确定、可回滚的结构迁移；
- 插件维护页保留幂等的数据检查、预览、修正结果和再次执行能力；
- 用户、登录和 Host 表修正不进入 Issue 插件；
- `oip_` 表、Issue 编号、链接计数、点检和附属报告修正继续由插件拥有；
- 所有修正先报告影响数量，危险操作要求备份与管理员 capability，不复制 SQLite 专用 SQL。

### legacy 八项修正的迁移矩阵

| legacy task | 新归属 | 当前处理 | 进入维护页的条件 |
| --- | --- | --- | --- |
| `schema` 表结构补全 | Pah 安装/升级 migration | 不复制旧页面中的“点击建表”；安装器负责确定性 DDL，维护页只读展示版本与缺失项 | Host 提供插件 migration 状态/health check 后 |
| `checkpoints` 点检修正 | Issue 插件 | 改写为 `oip_checkpoint` 的 PostgreSQL 幂等检查；不再补 SQLite 列 | 点检 Entity/Service 已迁，可作为首个 repair 纵切 |
| `links` Issue 链接修正 | Issue 插件 | 针对 `oip_issue_list_link` 补原始归属链接、去重并校正 `oip_issue.listCount` | Issue、列表链接实体和访问控制均已迁 |
| `dict` 字典补全 | COOL + Issue adapter | COOL 管共享数据；插件检查 namespace、固定协议值、核心类型和引用，不迁 legacy `tags` SQL | Host 字典写入/停用 adapter 与 capability 完成后 |
| `users` 用户权限补全 | Host | 删除 Issue 版按钮；legacy user/systemRole 只在导入转换器映射为 COOL 用户/角色 | 不进入 Issue 维护页 |
| `issueNo` 编号去重 | Issue 插件 | 抽成纯编号规划算法，再由事务执行临时号/重排；默认只预览受影响年份与数量 | 编号算法测试、备份提示和管理员 capability 完成后 |
| `linkAttention` 关注系数迁移 | legacy 导入器 | PostgreSQL 新表只使用 `attentionLevel`；`voided*` 兼容只在旧库导入时执行一次 | 不作为日常维护按钮 |
| `reports` 8D 报告修正 | Issue 插件 | 等 `oip_eight_d_report` 迁入后，保留“孤立报告不删正文、旧 Issue 内容幂等补迁”规则 | 8D Entity/Service/测试完成后 |

“全部执行”不能原样迁移。新端应按当前已安装能力生成计划，只执行插件拥有且已通过前置检查的 task；Host 与一次性导入任务不得混入日常“全部修正”。

## 4. Issue 字典分类

COOL 的 `dict_type` / `dict_info` 提供类型、值、显示名、排序和父子关系，但没有 Open Issue 旧字典的 `enabled`、`tags`、协议值锁定和引用保护。不能把七组字典无条件塞入 COOL 后就删除领域规则。

| 旧分组 | 目标 | 规则 |
| --- | --- | --- |
| `issueCategory` 问题分类 | COOL 字典 | 使用产品命名空间 key；允许管理员增改排序；插件校验引用，删除改为受控停用/迁移 |
| `detectionPhase` 发现阶段 | COOL 字典 | 同上；汽车/软件预设由插件安装器写入，不把 preset tags 变成 Host 通用概念 |
| `severity` 重要度 | 插件固定协议 + COOL 显示名覆盖 | 值、顺序和启用状态固定为四档，只允许改显示名；Host 缺失或配置非法时回退插件常量 |
| `priority` 紧急度 | 插件固定协议 + COOL 显示名覆盖 | 同重要度；排序和领域校验永远由插件代码负责 |
| `closeReason` 关闭理由 | COOL 字典 + 插件状态规则 | 可扩展显示项，但关闭状态机、历史引用和核心 reason 保护由插件负责 |
| `listType` 点检表类型 | COOL 字典 + 插件核心类型保护 | 核心类型稳定；允许扩展类型，但成员范围、组织范围和默认行为不能由显示字典决定 |
| `orgUnitType` 组织类型 | 不新建 Issue 字典 | 新数据复用 COOL 部门/组织；仅在 legacy 导入时做兼容映射 |

命名空间先固定为 `phoenix-open-issue.<group>`。页面只通过 Issue 的字典 adapter 读取，不直接散落调用 `service.dict.info`。

### 定制边界

- COOL 负责共享存储、管理入口、排序和常规翻译；
- 插件负责稳定 value、默认值、允许值、状态联动、引用检查、历史兼容和 preset；
- COOL 当前没有“受保护字典类型”能力，因此 `severity`、`priority` 以及核心 `listType` 不能开放为无约束的通用 CRUD；
- 第一阶段保留内置 fallback，确保 Host 尚未配置字典时页面仍可工作；
- 后续若 Host 增加 namespace owner、只读项、停用和引用检查扩展点，再减少插件 adapter。

## 5. 单元测试入口安全边界

旧实现直接从独立仓库启动 `pnpm exec vitest`。插件版保留功能，但不接受客户端传入命令、路径或参数：

1. manifest 声明允许的测试集合；
2. 服务端只执行当前插件安装目录内的固定 runner；
3. 仅 Host 系统管理员且开发/内网策略开启时可运行；
4. 同一插件单实例运行，设置总超时和输出上限；
5. 报告写入 Host 任务/文件能力分配的目录，并带插件 ID、run ID 和审计记录；
6. 生产环境默认只展示最近一次 CI/安装验收结果，不启动包管理器进程。

这样保留旧页面的可见能力，同时避免把通用命令执行器带入生产 Host。Admin 插件只物化一个可见“维护”菜单；`/open-issue/test-runner` 是指向同一 `maintenance.vue` 的隐藏兼容深链，不是第二个 View。

## 6. 迁移顺序

1. 原样迁移 Function View 与依赖闭包，接 `oip_function`；
2. 恢复 Function 与 Issue 的显示、选择和历史关联；
3. 把数据字典页面拆为 Issue 维护页，先接只读/可验证 adapter，再开放受保护的写操作；
4. 恢复插件数据检查/修正页，以 PostgreSQL migration 和幂等 repair service 重写执行端；
5. 将单元测试区并入维护 View，最后接受控 runner；
6. 与 legacy 双开抽样对照页面布局、弹窗字段和交互顺序。

## 7. Pah contribution 重物化规则

已启用插件重新登记 manifest，只更新登记内容，不等于把新增 route/navigation contribution 写入 Host 菜单。每次新增、删除或改名路由后必须：

1. 先通过 manifest 校验和 Host 类型/构建门禁；
2. 对开发实例执行受控“停用→启用”，触发 contribution 重物化；
3. 查询或在 `/pah/plugins` 核对预期的 route ID/数量；
4. 真实访问新增 URL，刷新后仍可达；
5. 停用时入口消失、再次启用后恢复，业务数据不删除。

只重启 Vite、重新登记 manifest 或直接修改菜单表都不能替代这套生命周期验证。
