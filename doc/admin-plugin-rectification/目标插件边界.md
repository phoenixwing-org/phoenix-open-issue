# 目标插件边界

状态：active

## 1. 总体原则

Open Issue 作为一个逻辑插件发布，构建时分成前端插件和后端插件。独立版与 Admin 插件版共享领域规则和尽可能多的业务视图；二者只在外壳与平台适配层分叉。

Phoenix Admin 已经适配 Phoenix Wing 0.6，因此 Open Issue 的迁移对象是**业务页面**，不是独立版 AppShell，也不是另一套 Wing Workbench。

```text
Open Issue 领域与业务页面
├─ standalone adapter → 独立 Router / 登录 / Express / SQLite 或 PG
└─ admin adapter
   ├─ web plugin  → Phoenix Admin 的 Main View、菜单和路由贡献
   └─ node plugin → Midway Controller、Service、Entity、migration

Phoenix Admin Host
├─ Wing 工作台壳、Tab、导航与可选区域
├─ 登录、会话、用户、部门、系统角色和能力上限
├─ 字典、文件、任务、参数、备份与审计等平台能力
└─ 插件登记、启停、升级、卸载和受控加载
```

## 2. 前端插件负责什么

前端插件拥有：

- 列表管理、列表详情、Issue 查看/编辑、点检、推送等业务页面；
- 页面内部组件、字段、列配置、筛选、分页、弹窗和业务交互；
- Open Issue 自有 Store 和页面状态；
- 前端业务权限判定的展示镜像；
- 路由、菜单、页面标题和可选 Wing 区域的贡献声明；
- 对 Host SDK 的单一适配入口。

前端插件不拥有：

- `App.vue`、全局 `AppShell`、登录页或第二套工作台；
- 第二个 Vue、Pinia、Vue Router、Element Plus 或 Phoenix Wing 运行时；
- Host 用户、部门、系统角色和全局菜单状态；
- 自己的顶层主题/显示设置；
- 为适配 Host 而重排业务页面的权力。

Host 应向前端插件提供稳定上下文，而不是要求页面直接依赖 Host 内部目录：

- 当前 actor 与 capability 查询；
- 带 Host 会话和 correlation ID 的请求客户端；
- 路由跳转、Tab 打开/关闭和页面标题；
- 用户/部门选择器、字典、文件、通知和确认框；
- 宿主主题 token 与国际化；
- 审计关联和错误呈现。

第一版中，业务 View 应完整渲染在 Main 区域。插件可以声明 Primary/Secondary/Properties/Bottom，但默认不声明；任何拆分都必须通过页面保真评审。

### 2.1 页面迁移的两遍规则

第一遍是“原样迁移”：

- 按页面的实际依赖闭包一起迁入，包括组件、样式、Store、composable、列配置和业务弹层；
- 保持 Vue template、页面 scoped style、操作位置、弹层形态和页面内部路由行为不变；
- 在插件外围提供临时兼容 facade，使原页面可以在 Host Main 区域先运行；
- 不在这一遍引入 Host 专属布局，不顺手重命名、拆组件、改样式或调整交互。

第二遍是“接口替换”：

- 保持页面外观和交互金线不变；
- 逐项把原请求客户端、auth store、用户/部门、字典、路由和平台服务切到 Host adapter；
- 优先保持页面当前调用签名，在 adapter 内完成 Host API 字段和错误格式转换；
- 一个接口替换完成并通过回归后再替换下一个，避免页面迁移与接口迁移同时失真。

只有两遍迁移都完成后，才讨论是否使用更多 Wing 区域或升级视觉设计。

## 3. 后端插件负责什么

后端插件拥有：

- Open Issue Controller、Domain Service、Repository/Entity；
- `oip_` 表、索引、migration 和数据完整性检查；
- 列表成员资源角色与 Issue 可见性；
- Issue、点检、推送、关注、业务字典扩展等领域规则；
- 插件健康检查、启停钩子和卸载数据清单；
- 调用 Host 审计、任务、文件、字典等能力的适配层。

后端插件不拥有：

- 密码、JWT、刷新令牌或第二份登录；
- Host 用户、部门、系统角色、菜单和统一审计表；
- 任意执行上传源码的能力；
- 宿主通用上传、定时任务、参数、备份的重复实现。

每个请求的权限顺序保持为：Host 会话与账户状态 → Host capability 上限 → Open Issue 资源角色 → 领域不变量 → Host 审计。

## 4. Host 负责什么

Host 负责稳定平台能力和插件生命周期，不负责 Open Issue 的具体页面与领域实现：

- Host 解析 manifest，登记菜单、路由、能力码、migration 和健康检查；
- Host 提供唯一工作台壳、唯一 Router/Pinia/Vue 实例和统一会话；
- Host 在编译期或受控重启时加载插件入口；
- Host 禁用插件时撤下菜单、路由、任务和写入口，但默认保留 `oip_` 数据；
- Host 只保存通用注册表和适配代码，不复制业务 View/Service。

`phoenix-admin-vue/src/modules/open-issue`、`phoenix-admin-node/src/modules/open-issue` 和 Host 内的产品 PrototypeManifest 都必须删除。开发期也不在 Host Git 中提交产品桥；本地联调通过未跟踪链接、安装包或通用加载入口完成。Host 类型转换属于通用 SDK，产品 adapter 属于插件仓。

## 5. 独立版与插件版如何共享

建议按三层拆分，而不是复制目录：

| 层 | 共享程度 | 说明 |
|---|---|---|
| 领域层 | 全共享 | 类型、权限、算法、校验与领域不变量 |
| 业务 UI 层 | 高共享 | 原页面和组件；通过 ports 获取请求、actor、路由与平台能力 |
| 平台适配层 | 分开 | standalone 与 admin 分别提供实现 |

允许出现少量宿主专属页面，例如历史迁移确认、插件健康和生命周期管理；这些属于 Host 管理面，不应混入普通 Open Issue 业务页面，也不能被用来替代原设置或列表页面。

## 6. 编译期插件与在线插件的关系

建议按同一 manifest 契约分两步：

1. **编译期插件**：Host 以 workspace/package dependency 引入前后端入口，构建时完成路由与模块注册。目标是先证明代码归属、页面保真、身份和数据边界正确。
2. **受控安装包**：在相同入口和 manifest 上增加签名、哈希、SBOM、兼容校验、migration preview、原子落盘和受控重启。

第二步不应再改写业务页面；它只改变插件如何交付和激活。
