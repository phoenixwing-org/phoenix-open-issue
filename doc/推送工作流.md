# 推送工作流设计

> 当前 v0.1 只记录推送日志，缺确认/拒绝机制。本文档是 v0.2 推送重构方案。

---

## 当前 v0.1 推送（不完整）

```
源列表 A ──推送记录──▶ 目标列表 B
         (仅写 push_records，无实际效果)
```

**问题**：Issue 没有真正进入目标列表，目标列表成员看不到推送内容。

---

## v0.2 完整推送流程

```
┌──────────────────────────────────────────────────────┐
│                   推送流程                            │
│                                                      │
│  源列表 A                  目标列表 B                 │
│  ┌──────┐                ┌──────┐                    │
│  │Issue1│──推送────────▶│ 待确认 │                   │
│  │Issue2│  (pending)    │ 队列  │                    │
│  └──────┘                └──┬───┘                    │
│                             │                        │
│                    ┌────────▼────────┐               │
│                    │  Owner / 管理员  │               │
│                    │     确认        │               │
│                    └──┬──────────┬──┘               │
│                       │          │                   │
│                   ✅ 接受     ❌ 拒绝                 │
│                       │          │                   │
│                       ▼          ▼                   │
│               Issue 进入    推送关闭                 │
│               目标列表      下次可重推                │
│               全员可见                               │
└──────────────────────────────────────────────────────┘
```

### 规则

1. 源列表成员选择 Issue → 推送到目标列表（需成员重叠验证）
2. 推送后状态为 `pending`，仅源列表和推送发起者可见
3. **目标列表 Owner** 可以看到并处理待确认的推送（不是任意成员）
4. Owner 点击 **接受** → Issue 出现在目标列表，全员可见。**同时仍保留在源列表**（一个 Issue 可属于多个列表）
5. Owner 点击 **拒绝** → 推送关闭，Issue 留在源列表
6. 被拒绝的推送可以**重新推送**（创建新推送记录）
7. 接受后，Issue 在目标列表显示来源标注："来自 [源列表名]"

## 数据模型变更

### 新增表：issue_list_links（Issue 多列表关联）

```sql
-- 一条 Issue 可属于多个列表。issues.list_id 仍为主列表（创建时所属）
-- 推送接受后在此表插入记录，将 Issue 关联到目标列表
CREATE TABLE issue_list_links (
  id TEXT PRIMARY KEY,
  issue_id TEXT NOT NULL,
  list_id TEXT NOT NULL,
  linked_at TEXT DEFAULT (datetime('now')),
  linked_by TEXT NOT NULL          -- 推送发起人
);
```

### push_records 表（v0.2）

```sql
CREATE TABLE push_records (
  id TEXT PRIMARY KEY,
  from_list_id TEXT NOT NULL,     -- 源列表
  to_list_id TEXT NOT NULL,       -- 目标列表
  issue_id TEXT NOT NULL,         -- 被推送的 Issue
  pushed_by TEXT NOT NULL,        -- 推送发起人
  pushed_at TEXT DEFAULT (datetime('now')),
  status TEXT NOT NULL DEFAULT 'pending',  -- pending | accepted | rejected
  handled_by TEXT,                -- 确认/拒绝人
  handled_at TEXT,                -- 操作时间
  reject_reason TEXT,             -- 拒绝理由
  note TEXT DEFAULT ''            -- 推送备注
);
```

### 接受后的处理

**方案：引用（一条 Issue 关联多个 List，不复制数据）**

```
推送被接受 →
  1. Issue 保持在源列表，不动、不复制
  2. 在 issue_list_links 表插入引用记录（issue_id → 目标 list_id）
  3. Issue 在源列表和目标列表均可查看、编辑（同一条数据，改一处双方可见）
  4. 目标列表展示时标记来源："📌 来自 [源列表名]"
  5. push_records 状态更新为 accepted
```

**好处**：
- 不冗余，编辑实时同步
- Checkpoint 时间线不分叉
- 源列表删除 Issue 时：若还有其它列表引用，仅断开源列表关联；若无引用则真删

## API 变更

### 新增端点

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/list/:id/pending-pushes` | 查看目标列表的待确认推送 |
| PUT | `/api/push/:id/accept` | 接受推送 |
| PUT | `/api/push/:id/reject` | 拒绝推送 `{ reason?: string }` |

### 修改端点

| Method | Path | 变更 |
|--------|------|------|
| POST | `/api/push` | 不再直接生效，改为创建 `pending` 状态推送 |
| GET | `/api/list/:listId/push-history` | 增加 status 筛选参数 |

### 接受推送具体逻辑

```
PUT /api/push/:id/accept
→ 校验：操作者是目标列表的 owner（仅 owner）
→ 校验：推送状态是 pending
→ 在 issue_list_links 中插入记录（关联 Issue 到目标列表）
→ 更新 push_records.status = 'accepted'
→ 返回推送记录
```

### 拒绝推送具体逻辑

```
PUT /api/push/:id/reject
→ 校验：操作者是目标列表的 owner（仅 owner）
→ 校验：推送状态是 pending
→ 更新 push_records.status = 'rejected'
→ 记录 handled_by, handled_at, reject_reason
→ 返回推送记录
```

## Core 算法补充

```ts
// packages/core/src/algorithms/push.ts

/** 检查推送是否可以被操作（确认/拒绝） */
export function canHandlePush(
  userId: string,
  push: { to_list_id: string; status: string },
  targetListMembers: Array<{ user_id: string; role: string }>,
): boolean {
  if (push.status !== 'pending') return false
  const role = checkListAccess(userId, targetListMembers)
  return role === 'owner'  // 仅 owner 可确认/拒绝推送
}
```

## 点检项关联讨论

推送接受后，Checkpoint 如何处理？

- **默认不复制**：目标列表重新建立点检节奏
- **可选复制最后一条**：带过来最近一次点检状态作为起点
- **未来可配置**：推送时可勾选 "同时复制点检记录"

推荐 v0.2 默认不复制，简单清晰。

## 字段锁定（源列表保护）

推送引用后，Issue 在两个列表中同时可见。为防止冲突，部分字段锁定为源列表专控：

```
┌──────────────────────────────────────────────┐
│  Issue: 采购服务器  📌 来自: 前端组7月点检    │
│                                              │
│  🔒 锁定（源列表专控）     🔓 开放（均可编辑） │
│  ┌─────────────────┐    ┌─────────────────┐  │
│  │ title           │    │ status          │  │
│  │ description     │    │ priority        │  │
│  │ severity        │    │ assigneeId      │  │
│  │ reporterId      │    │ dueDate         │  │
│  │ category        │    │ checkpoints     │  │
│  └─────────────────┘    └─────────────────┘  │
└──────────────────────────────────────────────┘
```

### 规则

| 视角 | 锁定字段 | 开放字段 | 说明 |
|------|---------|---------|------|
| **源列表** | 可编辑 | 可编辑 | 完整控制权 |
| **目标列表** | 只读 | 可编辑 | 状态、责任人、点检可独立更新 |
| **其他引用列表** | 只读 | 只读 | viewer 同权限 |

### 锁定字段（源列表专控）

这些是 Issue 的定义属性，只有源列表的 editor+ 可修改：

```
title, description, severity, category,
reporterId, detectionPhase, rootCause, correctiveAction
```

### 开放字段（各列表独立可控）

这些是 Issue 的执行属性，每个引用列表可独立修改：

```
status, assigneeId, dueDate, completedAt, 
closeReason, checkpoints
```

### 数据存储

`issue_list_links` 表增加开放字段列（覆盖值）：

```sql
CREATE TABLE issue_list_links (
  id TEXT PRIMARY KEY,
  issue_id TEXT NOT NULL,
  list_id TEXT NOT NULL,
  linked_at TEXT DEFAULT (datetime('now')),
  linked_by TEXT NOT NULL,
  -- 各列表独立覆盖的值（NULL = 用 Issue 主表默认值）
  statusOverride TEXT,             -- 此列表中的状态
  assigneeOverride TEXT,           -- 此列表中的责任人
  dueDateOverride TEXT             -- 此列表中的计划完成日
);
```

查询时：`COALESCE(link.statusOverride, issue.status)` — 覆盖值优先。

**简化版 v0.2**：不做字段级覆盖，先开放所有字段均可编辑，信任协作。字段锁定留到 v0.3。
