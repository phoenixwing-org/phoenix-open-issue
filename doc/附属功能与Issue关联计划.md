# Issue 扩展能力计划：定向推送与附属关联

状态：current

Owner：Open Issue maintainers

适用版本：0.6.1

最后核验：2026-07-31

本文记录 0.6.1 已落地的两项相互独立、都不侵入 Issue 核心模型的扩展能力：

1. 用户定向推送：解决“想把 Issue 推给另一个人，但不知道或无权访问对方列表”的问题。
2. 附属功能关联：让 8D、财务、电子等专业记录可选关联 Issue。

## 第一部分：用户定向推送

### 1. 现状与目标

当前推送只能选择当前用户有权看到的目标列表，不适合“甲把问题交给乙，由乙决定放入哪个工作列表”的协作方式。

新增“推送给用户”模式后：发送人只选择接收人，不需要查看接收人的列表；接收人接受时再选择自己有权管理的目标列表。现有“推送到列表”模式继续保留。

### 2. 产品规则

- 发送人必须拥有来源 Issue 的推送权限。
- 接收人必须是启用且已批准的系统用户；第一阶段只选择单个接收人。
- 待接收期间不改变 Issue 的列表关系，也不自动授予任何权限。
- 接收人接受时，从自己有权接收 Issue 的列表中选择一个目标列表。
- 接收后仍沿用 Issue 链接机制，不复制 Issue。
- 接收人可以拒绝；发送人可以在处理前撤回。
- 发送人只能看到推送状态，不得借此获知接收人的私有列表名称或成员信息。
- Issue 关联到目标列表后，只要操作者拥有该目标列表的推送权限，就能以当前列表为新来源继续转推；每次转推生成独立审计记录，允许个人、小组、科室、部门之间逐级流转。
- Issue 的状态与主字段全局共享；关注度属于 `Issue × 列表` 的局部状态，一个列表取消关注不会替其他列表取消关注。
- `listCount` 表示 Issue 当前关联的不同列表数量，不把重复推送次数解释为重要度；重要度仍使用独立内置字段。

### 2.1 业务语义与设计理由

协作中的 Issue 同时包含两类信息，必须分别处理：

- **共享事实**：标题、内容、状态、责任人和点检记录描述的是同一件事情，在所有关联列表中保持一致。某一处理人完成 Issue 后，其他列表看到同一个完成结果。
- **局部工作状态**：关注度表达某个列表是否还需要持续跟进。个人、小组已经不关注，不代表科室或部门也应自动取消关注，因此每个 `Issue × 列表` 独立维护。

转推表示责任边界或可见范围继续扩展，例如“个人 → 小组 → 科室 → 部门 → 其他”。同一 Issue 可以多次转推，每次形成独立推送记录用于审批和审计；接受后只增加目标列表关联，不复制 Issue。推送次数容易受重复提醒、拒绝后重试等操作影响，只能作为传播或流转线索，不能替代重要度、紧急度或关注度。

### 3. 数据模型建议

扩展现有 `pushRecords`，而不是另建一套推送表：

```ts
targetType: 'list' | 'user'
toListId: string | null
toUserId: string | null
```

约束：

- `targetType=list`：`toListId` 必填、`toUserId` 为空，保持当前流程。
- `targetType=user` 且待处理：`toUserId` 必填、`toListId` 为空。
- 用户推送被接受后写入接收人选择的 `toListId`，同时保留 `toUserId` 作为审计信息。
- `status` 使用待处理、已接受、已拒绝、已撤回四种状态。
- SQLite 与 PostgreSQL 迁移、约束和索引必须保持一致。

### 4. API 与界面

- 推送弹窗提供“推送到列表 / 推送给用户”两个明确入口。
- 用户模式仅展示可接收的人员，不展示其列表。
- 个人推送历史同时显示“列表推送”和“发给我的推送”；列表收件箱仍只显示明确发往该列表的记录。
- 接受用户推送时必须选择目标列表；没有可接收列表时给出明确提示，不自动创建列表。
- 推送历史记录目标用户、最终目标列表、处理人和处理时间。

### 5. 权限与验收

- 无来源推送权限的用户不能发起两种推送。
- 只有指定接收人或系统管理员可以处理用户推送。
- 接收人只能选择自己具备接收权限的目标列表。
- 推送前后均不泄露双方无权查看的列表和 Issue 信息。
- 接受、拒绝、撤回和并发重复处理需要服务端幂等保护。
- 原有列表到列表推送及审批不回归。

### 6. 实施顺序

- [x] 补服务端目标类型、可空目标字段和 SQLite/PostgreSQL 迁移。
- [x] 收敛发送、接收、拒绝、撤回权限，并用 `status=pending` 条件更新防止重复处理。
- [x] 改造推送弹窗和个人推送历史，接受用户推送时选择目标列表。
- [x] 补推送状态筛选、最终列表与指定接收人审计信息。
- [x] 用隔离用户、系统查看用户、目标列表 editor/owner 覆盖越权与并发回归。

## 第二部分：附属功能关联

### 1. 背景

Open Issue 需要同时适用于科室周点检、日例会、项目例会、开发与测试等场景。8D 报告以及电子、财务等专业场景的数据属于可选附属能力，不应直接扩张 Issue 主表，也不应被定义为所有问题列表都必须填写的核心字段。

本阶段优先用最小模型验证真实使用方式，暂不建设通用关联表。Issue 主表提供通用 `extensions JSONB` 属性容器，但它不保存关联关系，也不用于动态定义 8D 等业务表单。

### 2. 已实现决定

附属功能自己的业务记录增加一个可空的 Issue 关联字段：

```ts
relatedIssueId?: string | null
```

约定如下：

- `null`：附属记录独立存在，不关联 Issue。
- 非空：附属记录关联一个已有 Issue。
- 字段放在附属功能记录上，不在 Issue 主表增加 `report8dId` 等反向字段。
- 使用明确名称 `relatedIssueId`，不使用含义不清的 `relatedId`。
- 同一个 Issue 默认可被多条附属记录引用；本阶段不加唯一约束。
- 不增加通用关联表；Issue 的 `extensions` 仅承载轻量扩展属性，附属记录仍使用自己的业务表和 `relatedIssueId`。

这一设计保持 Issue 核心模型稳定，也允许 8D、财务处置单或其他专业记录分别维护自己的生命周期和字段。

### 3. 数据库约定

每个需要关联 Issue 的附属业务表独立增加字段和普通索引：

| 数据库 | 字段建议 | 约束 |
|---|---|---|
| PostgreSQL | `relatedIssueId TEXT NULL` | 普通索引；应用层校验与维护修正 |
| SQLite | `relatedIssueId TEXT NULL` | 普通索引；应用层校验与维护修正 |

补充规则：

- 新建数据库直接包含 `eightDReports` 表与关联/创建人索引。
- 已有数据库通过版本化迁移建表；旧 Issue 中非空 D3/D4/D5-D6 内容按确定 ID 一次性复制为 8D 报告，不覆盖原正文。
- SQLite 与 PostgreSQL 的新增、修改、删除行为必须一致。
- 当前 Issue 删除是“转为已取消”而非物理删除，因此关联保持。若导入或人工维护造成目标 Issue 缺失，数据库修正会把报告转为独立报告，正文不删除。
- 当前 SQLite 兼容层关闭数据库外键，不伪造跨库不一致的 FK；由服务层写入校验、读取权限和维护任务共同保证。未来统一启用外键时再升级为 `ON DELETE SET NULL`。
- 数据库维护/表结构补全检查字段与索引；备份/受限导出包含有权访问的 8D 报告。

### 4. API 与权限

附属功能的创建和编辑接口接受可选字段：

```json
{
  "relatedIssueId": "issue-uuid-or-null"
}
```

服务端规则：

1. 未传字段或显式传 `null` 表示不关联。
2. 非空时必须验证目标 Issue 存在。
3. 操作者必须拥有目标 Issue 原列表的编辑权限，才能建立或更换关联；只读权限不足以改变关联。
4. 关联本身不授予 Issue 权限，也不提升附属功能权限。
5. 返回关联信息时，只有具备 Issue 查看权限的用户才能获得 Issue 标题等详情，避免通过关联泄露数据。

### 5. 前端交互

第一阶段只提供轻量入口：

- 附属功能编辑页提供“关联问题”选择器，允许清空。
- 选择器只展示当前用户有权查看的 Issue。
- Issue 详情页可以展示有权限查看的附属记录入口，但不把附属表单塞入 Issue 核心表单。
- 关联失效或用户无权查看时，不展示 Issue 标题；使用“未关联”或“无权查看关联问题”的明确状态。

### 6. 暂不处理

本阶段明确不实现：

- 一个附属记录关联多个 Issue。
- Issue 与任意业务对象之间的通用多对多关系。
- 在关联上记录角色、排序、备注、状态等元数据。
- 用 JSONB 动态定义 8D、财务、电子等业务表单。
- 通过关联关系自动继承双方权限。

### 7. 升级为关联表的条件

出现任一情况时再设计通用关联表：

- 一个记录需要关联多个 Issue，或 Issue 之间需要多种关系。
- 关联对象不再只有 Issue，需要支持多种目标类型。
- 关联本身需要保存类型、来源、顺序、备注、权限或状态。
- 需要跨模块统一查询、统计或审计关联变化。

升级时可把现有各业务表中的 `relatedIssueId` 迁移成关联表记录；在迁移完成前保留兼容读取，避免一次性破坏已上线模块。

### 8. 实施顺序

- [x] 选择 8D 报告作为首个真实附属功能，不建设空泛框架。
- [x] Core/API 使用 `relatedIssueId?: string | null`，一个 Issue 可有多份 8D 报告。
- [x] SQLite/PostgreSQL 增加一致的版本化迁移与索引，旧正文安全复制。
- [x] 服务层实现存在性、读取隔离、写权限、软删除与失效关联修正。
- [x] 独立 8D 页面支持新增、编辑、删除、关联、改绑、解绑；Issue 详情支持关联报告增删改查。
- [x] 增加独立报告、关联报告、越权访问、旧库迁移和双数据库迁移测试。
- [x] 纳入备份/受限导出和设置 → 数据库修正。
- [ ] 用更多财务/电子业务样例验证是否出现多对多或关联元数据需求，再决定是否建设通用关联表。

### 9. 验收标准

- 附属记录可以不关联 Issue，并能正常创建、编辑和查询。
- 有权限的用户可以关联、改绑和解绑一个 Issue。
- 无目标 Issue 查看权限的用户不能新建或修改关联，也不会看到受限 Issue 信息。
- 物理移除 Issue 后通过数据库修正将附属记录保留并把 `relatedIssueId` 置为 `NULL`；正常业务“删除”仅取消 Issue，不解除关联。
- PostgreSQL 是正式支持数据库；迁移不修改历史记录的业务内容。SQLite 仅保留过渡期测试/旧库兼容，后续按 `TODO.md` 独立移除。
- Issue 核心表单和 Core `Issue` 类型不再含 8D 专用字段；旧数据库列只为回滚兼容保留且不再写入。

## 实现位置与后续边界

- 数据表：`eightDReports`；核心字段是可空 `relatedIssueId`。Issue 另有 `extensions JSONB`，但附属关系不写入该属性容器。
- 用户入口：Ribbon → 8D 报告；Issue 详情 → 8D 报告区。
- 推送入口：Issue 推送弹窗中的“推送到列表 / 推送给用户”；用户接收统一在“推送历史”处理。
- 后台维护：设置 → 数据库修正 → 表结构补全 / 8D 附属报告修正。
- 后续仍不默认抽象通用关联表；只有出现多目标、多关系类型或关联元数据时才启动下一阶段设计。
