## 1. 目标

让同一套 Open Issue 后端可通过环境变量选择数据库：

```dotenv
# 单机、试用、轻量部署
DB_DRIVER=sqlite
DB_PATH=/var/lib/open-issue/open-issue.sqlite

# 多用户、正式部署
DB_DRIVER=postgres
DATABASE_URL=postgresql://openissue:password@127.0.0.1:5432/openissue
DB_POOL_MAX=10
```

目标不是运行时自动切换或双写，而是**启动时明确选择一种数据库**。配置错误应立即停止启动，禁止静默回退到 SQLite。

## 2. 结论

可以通过 `PnwDbAdapter` 实现，但不能只新增一个 PG 类。

当前 SQLite Adapter 是同步接口；Node.js PostgreSQL 驱动基于 Promise。要支持 PG，必须同步完成：

1. Adapter 接口异步化。
2. Service → Controller → Route 调用链异步化。
3. 手工 `BEGIN/COMMIT/ROLLBACK` 改为事务回调。
4. 清理 SQLite 专属 SQL。
5. 处理 PostgreSQL camelCase 标识符必须加双引号的问题。
6. 建立 SQLite / PostgreSQL 双数据库集成测试。

不采用“同步阻塞 PostgreSQL”或 Worker + Atomics 模拟同步；这会增加死锁、性能和运维风险。

## 3. 当前差距

代码盘点：

- 约 308 次 `db.get/all/run/exec` 调用。
- 4 处手工事务。
- SQLite 专属能力包括 `PRAGMA`、`sqlite_master`、`strftime`、`INSERT OR REPLACE/IGNORE`、`datetime('now')`。
- SQL 使用 `?` 参数，PG 使用 `$1/$2/...`。
- SQL/JSON 字段使用 camelCase；PG 未加引号会自动折叠为小写。
- 当前 schema/migrations 与 SQLite 元数据结构绑定。

因此适配工作应分阶段完成，不能一次替换数据库后靠运行时排错。

## 4. PnwDbAdapter 设计

先在本项目成熟，再迁移到 `phoenix-wing/src/db/`。项目内统一使用 `pnw` 前缀。

```ts
export type PnwDbDialect = 'sqlite' | 'postgres'

export interface PnwDbResult {
  changes: number
}

export interface PnwDbExecutor {
  get<T>(sql: string, params?: readonly unknown[]): Promise<T | undefined>
  all<T>(sql: string, params?: readonly unknown[]): Promise<T[]>
  run(sql: string, params?: readonly unknown[]): Promise<PnwDbResult>
  exec(sql: string): Promise<void>
}

export interface PnwDbAdapter extends PnwDbExecutor {
  readonly dialect: PnwDbDialect
  transaction<T>(fn: (tx: PnwDbExecutor) => Promise<T>): Promise<T>
  tableExists(table: string): Promise<boolean>
  columnNames(table: string): Promise<Set<string>>
  indexExists(index: string): Promise<boolean>
  close(): Promise<void>
}
```

建议项目内文件：

```text
packages/server/src/db/pnw/
├── pnwDbTypes.ts
├── pnwDbFactory.ts
├── pnwSqliteAdapter.ts
├── pnwPostgresAdapter.ts
├── pnwSqlParams.ts
└── pnwMigrationRunner.ts
```

稳定后迁移到 phoenix-wing：

```text
phoenix-wing/src/db/
├── pnwDbTypes.ts
├── pnwSqliteAdapter.ts
├── pnwPostgresAdapter.ts
└── pnwDbFactory.ts
```

业务 schema 和 Open Issue migrations 必须留在本项目，不进入 phoenix-wing。

## 5. SQL 约定

### 5.1 标识符

继续遵循现有规范：SQL 列名、JSON 字段使用 camelCase。

所有表名和列名必须加双引号：

```sql
SELECT "issueNo", "listId" FROM "issues" WHERE "id" = ?
```

SQLite 和 PostgreSQL 都支持该写法，避免 PG 将 `listId` 折叠成 `listid`。

动态排序字段必须继续使用白名单，不允许直接拼接用户输入。

### 5.2 参数

业务 SQL 暂以 `?` 为统一占位符。PG Adapter 使用一个带字符串/注释识别的转换器编译为 `$1/$2/...`，禁止简单正则全局替换。

转换器需要单元测试：

- 普通参数。
- 字符串中的问号不转换。
- SQL 注释中的问号不转换。
- 多参数顺序正确。

### 5.3 时间

优先由应用生成 ISO 8601 时间并作为参数写入。DDL 默认值统一使用 `CURRENT_TIMESTAMP`。

移除业务 SQL 中的：

```sql
datetime('now')
strftime(...)
```

### 5.4 Upsert

将 `INSERT OR REPLACE/IGNORE` 改为显式 `ON CONFLICT`。SQLite 3 和 PostgreSQL 都支持：

```sql
INSERT INTO "systemFlags" ("key", "value") VALUES (?, ?)
ON CONFLICT ("key") DO UPDATE SET "value" = EXCLUDED."value"
```

### 5.5 事务

禁止 Service 直接执行 `BEGIN/COMMIT/ROLLBACK`：

```ts
await db.transaction(async tx => {
  await tx.run(...)
  await tx.run(...)
})
```

PG Adapter 必须保证事务内查询固定使用同一个 PoolClient。

## 6. Schema 与迁移

拆分为：

```text
db/schema/common.ts       逻辑表定义
db/schema/sqlite.ts       SQLite DDL
db/schema/postgres.ts     PostgreSQL DDL
db/migrations/common/     数据迁移
db/migrations/sqlite/     SQLite 结构迁移
db/migrations/postgres/   PG 结构迁移
```

新增迁移记录表：

```sql
"schemaMigrations" (
  "id" TEXT PRIMARY KEY,
  "appliedAt" TEXT NOT NULL
)
```

迁移要求：

- 有固定 ID，严格排序。
- 可重复启动，不重复执行。
- 失败必须回滚并阻止服务启动。
- 不再依赖删除数据库重建。

### Phase D：双数据库测试矩阵

同一套集成测试分别执行：

```text
DB_DRIVER=sqlite
DB_DRIVER=postgres
```

覆盖：

- schema 初始化和重复启动。
- 用户注册/审批/禁用。
- 列表权限。
- Issue 创建、编辑、取消和多列表链接。
- 点检、推送审批、关注度。

- 事务失败回滚。

PG 测试建议使用 Testcontainers；CI 没有 Docker 时可使用专用测试库。

### Phase E：数据迁移

不直接复制 SQLite 文件。使用设置页已有的 JSON 导出和导入完成迁移，不再新增重复的 CLI。迁移步骤、密码处理、数量校验和回滚方式见 [PostgreSQL 部署与 SQLite 数据迁移](PostgreSQL部署与迁移.md)。

## 8. 配置与部署

新增配置：

```dotenv
DB_DRIVER=sqlite
DB_PATH=../../data/open-issue.sqlite

# DB_DRIVER=postgres 时启用
```

日志只能显示 dialect、host、database，不得输出密码或完整 URL。

SQLite 继续作为默认值，保证现有用户无配置升级。PG 模式缺少 `DATABASE_URL` 时启动失败。

## 10. 风险与边界

| 风险 | 控制措施 |
|------|----------|
| 全链路异步改造范围大 | Phase A 只改执行模型，不同时改 SQL |
| PG camelCase 大小写 | 所有标识符统一双引号 |
| 参数转换误替换字符串 | 使用小型词法扫描器并单测 |
| 事务跨连接失效 | PG transaction 固定 PoolClient |
| 迁移破坏现有 SQLite | 双库测试、备份、禁止删库升级 |
| 两套 schema 漂移 | 迁移 ID、共享逻辑定义、CI 双矩阵 |
