## 4. 字典决策

### 4.1 当前不增加 Cool JSONB，也不建 Issue sidecar

当前运行时只需要 Cool 已有的 `type(name,key)` 与 `item(name,value,orderNum)`。`core/default/transitional`、preset、可定制字段、catalog 版本和默认值由 Issue manifest 持有；Pah ledger 保存每次 dry-run/reconcile 的 catalog hash、actor、计划和结果。这样既不把 Issue 产品语义硬编码进 Host，也不为尚不存在的运行时需求增加表。

本轮不在 `dict_info` 增加通用 JSONB。一个 JSONB 列无法自动提供字段级权限、引用保护或生命周期责任，反而会让 Cool 保存无法解释的产品策略。

本轮也不创建 `oip_dict_item_policy`。只有未来出现以下真实需求时，才新增 plugin-owned sidecar：按租户启停/retire、运行时引用保护、管理员必须在 Issue UI 查看 provenance，或策略不再能从 manifest + ledger 推导。该表必须以稳定 `(typeKey,itemValue)` 为键，不依赖 Cool 数字 ID；不能先把 Issue 特例晋升为 Host 公共表。

### 4.3 安装、升级和日常维护边界

目标 Pah install/upgrade lifecycle 与独立 reconcile 负责：

- 校验 namespace、catalog 唯一性和稳定 item value；
- 先返回 dry-run、catalog hash 与确认指纹；
- 在事务内重算指纹，只创建缺失 type/item；
- 保留已有名称、排序和未知管理员自定义项；重复 type/value 时 fail closed，不猜测合并；
- 写 Host-owned reconcile ledger；卸载默认保留字典；
- 只允许 Host 根管理员执行 lifecycle reconcile。

Maintenance 增加 Host-owned“字典初始化/补全”区，但不复制字典 CRUD：GET plan/status 展示缺失 type/item、冲突、保留的管理员定制和确认指纹；根管理员确认后调用独立 `POST /admin/pah/plugin/dictionary-reconcile`，Pah 在 SERIALIZABLE 事务内重算并写 ledger，过程文字进入 Host Output。该动作不得复用 Issue `maintenance:run`，不得由 Issue Controller 直写 `dict_type/dict_info`。

日常字典编辑、停用和删除仍走 Cool 字典页面/API/角色权限。Issue 没有第二套字典 CRUD，因此插件不能绕过 Cool 权限。根管理员进行 Pah lifecycle 物化是 Host 管理动作，不是插件用户的旁路 CRUD。

当前 dirty 候选只有 GET `/admin/pah/plugin/dictionary-plan`、GET `dictionary-records`，写 reconcile 仍耦合 `/enable`。已 enabled 插件不能再次执行 enable 状态转换，因此还缺上述独立 root-only POST；在它进入当前 Host 前，Maintenance 不能伪造“补全”成功。尚未完成项还包括正式 upgrade UI/状态机、真实库 plan/确认/二次零变化点检，以及有引用项的 retire/迁移产品流程。

## 5. 用户与权限决策

| legacy 权限 | Admin 目标 | 结论 |
| --- | --- | --- |
| `users.systemRole=admin/editor/viewer` | Cool 用户、角色组、菜单/API permission、Pah capability | obsolete；不迁 legacy 用户表或“补全用户权限”任务 |

## 6. 数据备份与 legacy 导入决策

### 6.1 A｜Host 全局可信 PostgreSQL 备份

不复制 legacy 独立备份页。Issue manifest 只声明自己的 `oip_*` 表，Pah 在 DDL/uninstall 前要求 Host 全局备份覆盖这些表。

静态备份范围不再只信 manifest 文本：插件 verifier 会从全部不可变 SQL migration 提取 `CREATE TABLE`，并与 TypeORM `@Entity` 和 `dataOwnership.tables` 做三方集合闭包。当前 9 张表（8 张业务表 + `oip_repair_ledger`）完全一致；migration 创建 schema-qualified 表、Host 命名空间表、未声明表，或 manifest 声明了没有 Entity/migration 的表都会 fail closed。独立 3 项回归覆盖正确集合与上述越界。这能证明“插件声明覆盖自己创建的表”，但仍不能证明某个真实 Host backup artifact 实际包含这些表。

dirty Node 候选设计了可信备份清单 adapter：HTTP 只提交安全的 backup ID；Node 从配置的绝对可信目录解析 manifest 和真实 artifact，校验数据库名、表范围、时间、恢复演练时间、文件 realpath、大小和 SHA-256，再生成进程内 proof。但该候选未提交、未迁入当前 Host；而且现有生产编排尚未完成从真实 backupId 经 provider 到 migration/uninstall verifier 的闭环，不能写成“生产已注入”。

这个候选 adapter 不执行 `pg_dump/pg_restore`。备份生成、保留、监控和恢复演练仍属于 Host 全局备份系统；在生产可信根目录、真实清单、责任人和独立 PostgreSQL restore drill 接入前，DDL、repair、import 与 uninstall 仍应 fail closed。

### 6.2 B｜transitional legacy data package

“数据备份用于迁移旧站数据”不能与 A 混成同一能力。B 是一次性迁移包：旧网站或 SQLite 只能由离线脚本导出版本化 JSON，再由 Maintenance 上传后执行 preview/plan；Web 不接收 SQLite 文件，也不恢复 legacy 独立备份页。

B 的边界如下：

- 禁止旧 `replace/merge` 和静默冲突；execute 必须有明确确认、fingerprint、TTL、事务重算与 import ledger；
- 只迁 8 张业务表，不导入 `oip_repair_ledger`；账号、密码、登录方式、角色和 Host 字典表一律不导入；
- 字典值交给 Pah reconcile；用户和部门只生成稳定 ID 映射、未映射与拒绝报告；
- 校验 format/schema/producer、UTF-8 SHA-256、bytes、字段白名单、重复键、引用、冲突、ID 映射和黄金查询；
- execute 的硬前置是 A 已有真实恢复证据，并先在两个隔离 PostgreSQL 数据库完成导入、二次拒绝/幂等、对账和恢复演练；
- 旧 SQLite 原件只读归档，记录 realpath、SHA-256、大小、owner 和保留期限；不得把原件直接交给 Admin 页面。

## 7. 数据库修正决策

| legacy task | 分类 | 当前处理 |
