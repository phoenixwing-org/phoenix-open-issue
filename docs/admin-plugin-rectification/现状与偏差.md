# 现状与偏差

状态：historical snapshot

核对日期：2026-07-31；2026-08-01 复核

> 本文保留首次发现“页面重写、Host 保存业务副本”问题时的快照。当前权威基线已经变更为两个 worktree：`phoenix-open-issue` 的 `legacy/2cdc5ea` 与 `phoenix-open-issue-admin` 的 `admin`。旧目录 `phoenix-open-issue-legacy`、旧提交和 Host 内置原型只用于解释历史偏差，不再是执行目标。

## 1. 核对范围

本次只做静态仓库核对，没有修改或运行 `legacy`、`phoenix-admin-vue`、`phoenix-admin-node` 的实现。

对比对象：

- `phoenix-open-issue-admin`：`admin` / `b3e2a35`
- `phoenix-open-issue-legacy`：`legacy` / `349e205`
- 独立 Web 基准候选：标签 `独立WEB` / `3e26537`
- `phoenix-admin-vue`：`codex/open-issue-plugin` / `d805d28`，且工作区存在未提交改动
- `phoenix-admin-node`：`codex/open-issue-plugin` / `0fd73df`

## 2. `admin` 当前真正完成的内容

`admin` 相对 `独立WEB` 的变化主要是文档和 `packages/admin-plugin` 契约原型。该包已经声明：

- 稳定的 `moduleId`、路由、导航、能力码和 Host 复用能力；
- 前后端入口与受控重启激活模式；
- migration、健康检查、`oip_` 数据所有权；
- 安装、启用、停用、卸载和默认保留数据的状态机。

这些内容有继续保留的价值，但 `packages/admin-plugin` 目前还是契约包，并没有提供可由 Host 消费的真实前端业务插件和后端业务插件。

## 3. `legacy` 为什么不只是 Layout 适配

`legacy` 相对 `独立WEB` 修改约 60 个文件，新增约 3000 行、删除约 900 行。变化不只发生在 `AppShell`：

- 新增 13 个 `Poi*Primary/Secondary/Bottom` 工作台组件；
- 重写 `AppShell`，让独立应用自己持有完整 `PnwWorkbenchShell`；
- 删除原 `AppToolbar`、`StatusBar` 和 Ribbon Shell；
- 修改路由、Tab 状态、显示偏好和主题桥接；
- 修改列表、列表详情、Issue 详情、组织、设置、功能表、推送历史等业务 View；
- 把列表筛选移出页面并放入 Primary；
- 把 Issue 点检时间线移出原详情结构并放入 Secondary；
- 把部分设置与修复操作移入 Primary/Bottom。

这类调整改变了用户寻找操作的位置、页面可见信息和响应式布局，因此属于页面重构。它可以作为 Wing 贡献机制的技术试验，但不能被描述为“仅适配 Layout”。

## 4. Admin Host 原型为什么也不是目标页面

`phoenix-admin-vue` 已在 `src/modules/open-issue/views` 中实现列表、列表详情、Issue 详情、推送历史和设置页面，`phoenix-admin-node` 也在 `src/modules/open-issue` 中实现对应的 Controller、Service 和 Entity。

这套原型证明了以下链路可行：

- Host 登录用户可以访问 Open Issue API；
- 菜单、能力码、资源角色和审计可以闭环；
- `oip_` 表和历史迁移可以落入 Host 数据库；
- 插件启停可以控制菜单和 API 可用性。

但它也引入了新的偏差：

- 前端页面改成新的 `oip-*` 标题、卡片、双栏 Properties 和表单布局；
- 列表、Issue、点检等交互与独立 Web 不同；
- Open Issue 业务源码被放进 Host 仓库，插件仓库反而只有 manifest；
- 前后端形成第二份实现，后续修复难以在独立版与插件版之间同步。

因此这套代码应被定义为**宿主闭环技术原型**，而不是产品完成态。

## 5. 根因判断

当前偏差不是某个 CSS 细节导致的，而是采用了错误的迁移单位：

> 目前以“重新实现一个符合 Wing/Admin 的页面”为迁移单位；正确单位应是“把既有业务页面剥离独立壳后，挂入 Host 的 Main 区域”。

对应的三个根因是：

1. 把 Wing 的可选区域当成页面必须拆分的目标；
2. 把 Host 原型目录当成业务插件的长期归属；
3. 没有先建立页面保真金线和允许变化清单。

## 6. 哪些成果保留，哪些暂停

| 类别 | 处理建议 |
|---|---|
| manifest、能力码、数据前缀、生命周期状态机 | 保留并继续收敛 |
| Host 的菜单贡献、启停门禁、用户映射、迁移台账 | 保留为 Host 能力与后端契约参考 |
| Host actor、资源角色、审计思路 | 保留 |
| `legacy` 的 Wing 0.6 兼容和贡献 Registry 经验 | 只作技术参考，按需摘取 |
| `legacy` 的页面拆区结果 | 暂停，不合入 Admin 产品线 |
| Host 中另写的 `oip-*` 页面 | 暂停扩展，待插件原页面替换 |
| Host 中 Open Issue 领域源码副本 | 暂停新增，后续迁回后端插件包 |

2026-08-01 用户进一步确认：Cool/Phoenix Admin 框架 Git 不得归档任何 Open Issue 业务代码或产品配置。两个 Host 分支先建立 archive ref，再把通用 Pah/Wing 成果重建为无产品代码的干净本地提交；Open Issue 业务只留在插件仓。
