# 点检日期设计

状态：current

Owner：Open Issue maintainers

适用版本：0.6.1+

最后核验：2026-07-31

## 需求结论

一个点检项包含两个不同的业务日期：

| 界面名称 | 字段 | 必填 | 含义 |
|---|---|---:|---|
| 点检日 | `checkpointDate` | 是 | 实际点检、复查或记录发生的日期；可编辑，是时间线的主日期 |
| 截止 | `deadline` | 否 | 希望该点检最晚完成的日期；可编辑、可清空，只用于截止提示和逾期判断 |

`createdAt`、`updatedAt` 继续由系统维护，仅作为审计时间，不代替点检日，也不在点检卡片和表格中作为主要业务日期展示。

允许“有点检日、没有截止日”。不要求截止日晚于或等于点检日：点检发生在截止日之后正是逾期场景，不应被表单拦截。

## 排序与逾期规则

- 时间线始终按 `checkpointDate` 排序；用户可切换最新优先或最早优先。
- `deadline` 为空时显示 `—`，不参与排序，也永不产生逾期。
- 只有状态为“待处理”且当前时间已经进入截止日的次日，才标记逾期。
- “已完成 / 已跳过 / 已作废”均不标记逾期。
- 日期只按 `YYYY-MM-DD` 保存和展示，不显示时分。

## 界面规则

- 新增和编辑弹窗同时提供“点检日”和“截止（可选）”；点检日默认当天，截止允许清空。
- 卡片模式日期行左侧显示 `截止 2026-07-31` 或 `截止 —`，右侧显示 `点检 2026-07-30`。
- 表格模式列顺序为 `截止 | 状态 | 内容 | 负责人 | 点检日`。
- 列表中的“最近点检”按点检日展示和截取；红色逾期样式只读取截止日。
- 复制时间线使用与表格相同的日期列和顺序。

## API 契约

新增点检：

```json
{
  "checkpointDate": "2026-07-30",
  "deadline": "2026-08-05",
  "description": "复查纠正措施",
  "responsibleUserId": "user-id"
}
```

无截止日时可以省略 `deadline` 或传 `null`。更新接口中：

- 不传 `deadline`：保持原值；
- 传日期：设置或修改截止日；
- 传 `null`：清空截止日。

后台拒绝不存在的日期或非 `YYYY-MM-DD` 格式。`checkpointDate` 不可为空，`deadline` 可为空。

## 数据库与升级

SQLite 与 PostgreSQL 的 `checkpoints` 表均新增可空列：

```sql
deadline TEXT NULL
```

升级过程遵循以下规则：

1. 新数据库直接创建 `deadline` 列。
2. 旧数据库幂等加列；首次升级时将旧 `checkpointDate` 复制到 `deadline`，保持升级前的计划日期和逾期效果。
3. SQLite 以 `systemFlags.migrate_checkpoint_deadline` 记录一次性回填完成；用户后来清空截止日，应用重启不会再次补回。
4. PostgreSQL 以 `schemaMigrations` 的固定迁移 ID `20260731-checkpoint-deadline` 保证只执行一次。
5. 导入 v0.6.1 以前的备份时，若记录完全没有 `deadline` 字段，则从 `checkpointDate` 继承；新版备份显式保存 `deadline: null` 时必须保持为空。

## 后台维护

设置 → 数据库修正提供两级维护：

- “表结构补全”检查 `checkpointDate / deadline` 列并执行待应用迁移；可重复执行。
- “点检数据修正”补全状态、顺序和审计时间，并将空字符串截止日规范为 `NULL`；它不会为无截止日记录自动生成日期。

维护结果需要报告无截止日记录数量，并明确“无截止日是合法数据，不参与逾期判断”。

## 验收条件

- 可新建仅有点检日、没有截止日的点检项。
- 可新增、修改、清空截止日，刷新和重启后保持不变。
- 修改点检日会改变时间线顺序；修改截止日不会改变顺序。
- 无截止日不标红；有截止日时按截止日次日起算逾期。
- 旧 SQLite、旧 PostgreSQL 和旧备份升级后均不丢失原日期含义。
- 卡片、表格、列表紧凑列、复制内容、API 和文档使用同一套日期语义。
